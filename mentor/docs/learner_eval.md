# 使用者互動與評估（Learner Evaluation）— docs/learner_eval.md

> 入口：../CLAUDE.md。本檔涵蓋與使用者互動、深讀評估、學習者狀態、習慣統計、極輕量模式的完整規則。

---

## 主線 2｜學習者狀態讀取 → 互動後更新（使用者端）
1. `python3 mentor.py learner_state` → 評估進度、自動升降級（升降至多一級/次；不低於地板；只計 depth≥2 的 pass）。
2. 與使用者互動（teaser / deep / 回答評估）。
3. 使用者回答 → 用 rubric 判讀 → `review` 記錄裁決；通過（depth≥2）則推進、盲區解除。
4. 提問方式一律照下方「蘇格拉底式提問規則」；互動時順便驗收相關舊概念，見「順帶驗收舊概念」。

---

## 深度問答與評估（Interactive Assessment）
- 使用者 `deep <id>` → `python3 mentor.py deep <id>` 出深度思考題。
- 用 `rubric <id>` 讀審查標準，對照回答判讀：
  - 正確且有深度 → `review --paper <id> --result pass --depth <2-4> --note "..."`。
  - 有誤或敷衍 → `review --paper <id> --result fail --depth <0-1> --blindspots "..." --note "..."`，指出盲區給提示。
- **絕對禁止**：未答題或未展現足夠理解就標記通過；pass 但 depth<2 程式不會推進領域。
- **機制級精準度優先**：使用者常見的偏差模式寫在 `profile.md`（例如「框架級直覺強、機制細節有偏差」）。
  評估時務必逐一檢查並校正機制細節（演算法怎麼算、公式乘什麼、為何成立）。論文在 paper-kb 裡時，先 `kb_search`/`kb_read` 核對原文再下判斷（`docs/paper_kb.md`）。

## 學習者畫像原則（升降級保守化）
- 非在 rubric 上展現 **機制層（depth≥2）** 理解不升級（已程式 enforce）；優先「把機制講精準」而非「衝廣度」。
- 依 `profile.md` 的自評決定起點；用跨域鏡子與機制校正把「看過」轉為「講得對」。

## 瑣碎記憶（Raw Interaction Journal）— 每次互動後必做
- **時機**：每當使用者有實質互動（deep 作答、機制辯證、提出想法/質疑），完成 `review` 與記憶更新後，用 `journal_add` 逐字保存原始對話。日常推播若無使用者回話可略過。
- **指令**：
  ```
  python3 mentor.py journal_add \
      --user "使用者原話1||使用者原話2||..." \
      --mentor "導師這次的回應/裁決摘要" \
      --tag <短標籤> --domain <cv|llm|diffusion> --title "一句主題"
  ```
  `--user` 逐字保留、不改寫；檔名自動 `journal/YYYY-MM-DD_HHMMSS_<tag>.md`；自動內嵌記憶快照。
- **檢視**：`journal_list`。`mem_add`/`review` 萃取要點，`journal_add` 保存原礦，兩者都要做。

## 論文閱讀.xlsx 自動登錄（2026-11-02 新增）— done 收尾必做
> 目的：除了文獻歸類，更要讓使用者**好幾年後回來看，仍讀得懂當時在問什麼、思考怎麼轉彎**。所以不能只有精煉後的語言。

- **觸發**：使用者說 done，且當次**真的有討論某篇論文**（有 `review`／`journal_add`）→ 每篇論文執行一次。只有 `light_checkin` 的日子不寫。
- **順序**：`recall`（若有）→ `review` → `journal_add` → **`paper_xlsx`** → `kb_queue`（若有 paper-kb，見 `docs/paper_kb.md`）→ `light_checkin` → 對話總結。
- **欄位鐵則**：
  | 欄 | 內容 | 規則 |
  |---|---|---|
  | C note | 使用者原話 | **只能是使用者打的字，逐字複製**。程式從 journal 擷取，禁止手打或改寫，也不加任何標記 |
  | D question | 導師的話 | 可精煉。依序寫：【當時的思考軌跡】（起點→被修正處→推到哪，含走錯的路）→【要解決的問題】【怎麼解】【關鍵機制】→【導師回應】→【未釐清】→【補強文獻】 |
  | M 對話脈絡 | 導師提問 ↔ 使用者原話，依對話順序交錯 | 導師端寫**當時實際的提問／陳述**（可略精簡，但保留問句本身）；使用者端只寫 `{U1}{U2}…` 佔位符，由程式代入逐字原文，每段剛好用一次（程式驗證） |
  | A/B/E/F/G | 日期、正式標題、URL、年份、第一作者 et al. | 標題、作者、年份查 arXiv 確認 |
  | H–L | 領域、判定（自動讀 learner.json）、paper_id、背景知識（預設 kg 先修）、journal 檔名 | 自動帶入，可用 flag 覆寫 |
- **指令**：先把 D、M 內容寫成暫存檔（放 `$HOME`，不要放進專案資料夾），再執行：
  ```
  python3 mentor.py paper_xlsx --pid <id> --journal <檔名1,檔名2> \
      --question $HOME/q.txt --context $HOME/ctx.txt \
      --title "正式標題" --year 2025 --authors "First Author et al."
  ```
  用 `--dry` 預覽；用 `--replace` 覆寫已存在的那一列；`--flush` 補寫佇列。
- **同一篇再次討論**：自動在原列追記，不新增列。C 欄直接接上新的原話；D、M 欄加 `[MM/DD 追記]`。
- **保護機制**：
  - 每次寫入前輪替備份到 `archive/xlsx_bak/`（10 格，覆寫最舊的一份）。
  - A 欄舊的 `NOW()` 公式會自動凍結成固定日期；遇到沒有日期快取的公式就停手不寫。
  - 如果 Excel 正開著這個檔（偵測到 `~$論文閱讀.xlsx`），就先存進 `paper_xlsx_pending.json`，下次自動補寫。
- **重要**：導師提問只存在當下對話裡，**必須在 done 當下寫 M 欄**，事後無法還原。

## 對話總結（Conversation Summary）— 收尾儀式（2026-07-09 新增）
> 當一段對話告一段落時，用 **chat（直接對話輸出，不寫檔）** 給出一份「結論」作為收尾。

- **觸發時機**：以下任一情形觸發——
  1. 使用者明確要求：說「給我總結」「我想要一個總結」「做個結論」等；
  2. 使用者說結束語：「今天就到這裡」「先這樣」「今天先這樣」之類；
  3. 你判斷對話差不多結束時，主動輸出。
- **結論內容（依序四段）**：
  1. **我們討論的點**：條列/摘述本次對話涵蓋的主題與關鍵往返。
  2. **我認為正確的地方**：肯定使用者講對、理解到位的部分（尤其機制層）。
  3. **還有什麼未釐清的地方**：指出仍有偏差、含糊或未展開的機制/盲區。
  4. **可以用什麼其他文獻補強**：針對未釐清處，建議具體可延伸的論文/理論/關鍵詞。
  5. **表達方式檢討**：針對本次對話，檢討使用者的表達方式——特別是我曾誤會使用者、或其話語有歧異之處。要**具體指出成因與改進建議**，例如「由於缺乏前言／主語／關鍵背景，我在沒有 X 資訊的狀況下誤解了你的意思；你之後可以改用 ooo 方式表達／先敘明前提／補上主語／xxx」。目的是幫助使用者把話講得更精準、減少來回誤解。若本次沒有明顯誤解或歧異，可簡短說明溝通順暢、無須調整。
- **形式**：直接在對話中輸出，繁體中文，精簡但完整；這是每次對話的收尾動作。若當次有實質互動，別忘了先照常做 `review`／`journal_add` 再輸出總結。

## 節流／精簡模式 — 已移除（2026-08-06）
> 舊版「連續 ≥4 天未互動自動放寬 push_log 組成」整套邏輯已刪除。理由：有了下面的**超輕量模式**（`light_checkin`）之後，「沒力氣深讀」這個情境已經有更直接的出口——使用者自己說一聲就好，不需要系統另外用天數去猜、去自動降低標準。少一套平行規則，行為更容易預測。
- `push_log` 現在**一律要求完整組成**（3 主領域 + ≥1 跨域 + 1 金融 + 3 wild），沒有放寬情境。
- `state.json` 裡殘留的 `throttle_mode`/`consecutive_active_days`/`last_active_date` 欄位是舊版遺跡，**程式碼已完全不讀它們**，不需要手動清除，但也別依賴它們判斷任何事。

## 習慣統計（Streak）— 只在使用者主動詢問時才顯示（2026-08-05 新增規則）
> 使用者反饋兩點：① 久未互動時「連續幾天」顯示是錯的、沒更新；② 主動秀出連續天數本身會造成壓力、降低動力。

- **鐵則：`daily_brief`、`learner_state`、`push_log`、`boot` 等自動流程一律不主動印出「連續 N 天」**。只有使用者明確詢問時才回答（例如「我連續幾天了」「我這陣子表現如何」）——執行 `python3 mentor.py streak` 讀取後如實告知，語氣中性、不帶壓力。
- `streak` 回傳「總互動天數」與「目前連續天數」，即時從真實紀錄推導（不依賴手動維護的計數器），永遠正確：
  - ✅ 算數：`teaser`/`deep`/`review` 留下的 episodic 狀態（`teaser_seen`/`reading`/`passed`/`failed`）、`push_log` 裡 `user_engaged=True` 的紀錄（`light_checkin` 打卡留下的）、`journal/` 逐字對話紀錄。
  - ❌ 不算數：`push_log` 裡**沒有**打卡標記的 main/xdomain/finance/wild——那只代表系統照排程把功課準備好了，不代表使用者真的看過。把兩者混為一談正是舊版「顯示錯誤」的病灶之一。
- 中斷不是失敗：`streak` 的措辭刻意不帶「連續」以外的評判字眼（不說「破功」「失敗」），中斷後回來就從新的一天繼續算。

## 極輕量模式（Ultra-Light Mode）與方向回饋（Interest Redirect）（2026-08-05 新增；2026-08-06 修訂）
> 動機：「讀一篇論文＋深讀問答」的完整模式門檻太高，容易變成不敢開始、或乾脆不點開。目標是先**養成「看」的習慣**，有餘裕再深入——完美不是每日的必要條件。

**鐵則（2026-08-06）：使用者回覆「done」／今天結束了 → 一律執行 `light_checkin`，不論今天是深讀還是只看一眼。**（2026-11-02 補：若有真的討論論文，`light_checkin` 之前先跑 `paper_xlsx`，見上方「論文閱讀.xlsx 自動登錄」）
- `light_checkin` 是**合併寫入**：若今天已經有正式 `push_log` 推播，只會加上「已打卡」標記，**不會**覆蓋掉當天的論文清單；若今天什麼都還沒記，才新建一筆空白打卡。因此隨時呼叫都安全，不用先判斷今天是哪種模式。
- 這樣設計是為了保證「有沒有互動」這件事本身**永遠會被記到**，不會因為忘記走哪條分支而漏掉一天。

**兩種內容深度，由「今天實際發生了什麼」事後決定，不是預先選擇：**
- **只有摘要／隨口一句／沒空深讀** → 只需要 `light_checkin [--note "..."]`；不需要 `deep`/`review`，不需要 `journal_add`，`--note` 只是一句話標記，不是詳細記錄。
- **有真的討論機制、或嘗試回答 `deep` 的問題** → 才需要**詳細記錄**：`review --paper <id> --result pass|fail --depth ...`（判讀機制理解）＋ `journal_add`（逐字保存對話）；`light_checkin` 仍照樣在收尾時執行一次，作為當天「有互動」的通用標記（`review` 產生的 episodic 紀錄本身也會被 streak 算到，兩者重複不影響正確性）。
- 判準就是使用者原話裡**是否真的討論到機制、或是否嘗試攻略了某篇論文**——不是你事先決定「今天走深讀」或「今天走輕量」，是對話結束時回頭看發生了什麼才決定要不要補 `review`/`journal_add`。
- 語氣：只需回「習慣 > 完美 ✓」一類的肯定語，不要暗示使用者「應該」做更多。

**方向回饋 → 重新指路**
使用者若回覆類似「我對 OO 領域感興趣」「最近 OO 領域感覺很 ooxx，想要 OO 方向」，視為主動指路訊號，處理順序：
1. 你（導師）依此**重新上網搜尋文獻**，構思新方向的候選推薦（不必等使用者確認就可以先找，但先別呈現）；
2. **詢問使用者**：「要現在看（深讀模式）還是之後再排？」——除非使用者已經在原話中直接講明「今天就要」/「現在」，此時跳過詢問、直接進入深讀模式；
3. **若使用者選「今天就要」**：照常規每日推播流程走（daily_brief → 搜尋 → check_dup → mem_add → push_log --dry → push_log），把新方向的候選正式呈現、深讀評估照舊；收尾一樣執行 `light_checkin`。
4. **若使用者沒有明講、或選「之後再排」**：執行 `python3 mentor.py light_checkin --interest "使用者原話或摘要"`，同時算完成今天、且把方向回饋寫入 `state.json` 的 `progress.redirect_note`；
5. `redirect_note` 存在時，下次 `daily_brief` 會主動印出「📍 待處理方向回饋」提示（不需要使用者重複講一次）；你依此重新搜尋、調整推薦方向並正式呈現後，執行 `python3 mentor.py redirect_clear` 清除提示。
- 兩種模式互不衝突、可並存：超輕量模式只是「今天先不深讀」，不影響已累積的導師記憶／知識圖譜／52 週藍圖，隔天想深入隨時可以接著原方向或新方向走。

## 蘇格拉底式提問規則（Socratic Mode）（2026-11-11 新增，借鏡 Jane Street `socratic-tutor`）
> 動機：回看 journal（如 2026-11-09 ood_maha），實際互動多是「使用者問→導師講→使用者複述→pass」，比較像上課。複述 ≠ 會用。改成**問題驅動**，讓使用者自己推出機制。

適用於 `deep` 作答、機制辯證、舊概念的追問。**例外**：使用者直接問「X 是什麼」這類一次性問題時照常回答；使用者說「直接告訴我」（just tell me）時，該題改為直接講解。

1. **一次只問一題**。問完立刻結束訊息，不附提示、不附範例答案、不在問題後面接著教。
2. **問題順序照使用者偏好**：先問「這個問題卡在哪／舊方法哪裡壞掉／為什麼重要」，再問機制，數學推導放最後（只當工具）。
3. **好問題的五種型**：預測結果（「如果拿掉 X 會怎樣？」）、解釋為什麼、找出似是而非說法的錯、套到新情境、連結兩個概念（可順勢接跨域鏡子）。
4. **答錯不給答案**：改問一個更窄、能讓他自己撞到矛盾的問題。同一點失敗 2–3 次才直接講，講完**立刻換個角度再問一次**。
5. **答對也要壓力測試**：偶爾反問「你確定嗎？那 X 的情況呢？」——講對的東西要守得住。
6. **只在真的推不出來的新知識上講解**，而且只講幾句，講完回到提問。
7. **複述不算通過**：使用者剛被告知答案後的複述，不能當作 depth≥2 的證據；要換角度再問一次答對才算。
8. 不灌迷湯：「不太對——如果 Y 成立，X 為什麼會發生？」勝過「很棒的嘗試！」

## 順帶驗收舊概念（Embedded Recall）（2026-11-11 新增；同日改版：不另外抽考）
> 動機：`ood_maha` 7/23 通過，11/9 又從頭學一次，「白化」同一點又卡住——通過後從沒被回頭驗收。
> 但**不另開考試**：每天在推播前/後塞一題，等於在門口加關卡，違反原子習慣「讓開始變容易」。
> 所以改成：**討論新論文時，順便驗收它用到的舊概念**——舊概念被新問題「用到」時才驗收，本來就是最自然的時機。

**每次使用者對某篇論文有實質互動時：**
1. 先跑 `python3 mentor.py recall_related --paper <這篇的 pid>`：列出這篇在知識圖譜上的先修（往上 3 層），以及同技能、已通過的舊概念，含上次評語和舊盲區（**只給導師看，不要貼給使用者**）。標「✅該驗收了」的優先。
2. 讀使用者的回答，對每個「該驗收」的舊概念判斷屬於哪一種：
   | 使用者的回答 | 做法 | 記錄 |
   |---|---|---|
   | **主動講到，而且講對**（沒被提示） | 不用另外問，這就是最好的「沒提示的回想」 | `recall --how mentioned --result pass` |
   | **有講到，但含糊或錯** | 照蘇格拉底規則深度追問（更窄的問題，不給答案） | 追問後講對 → `--how followup --result pass`；仍錯 → `--result fail --blindspots ".."` |
   | **沒講到，但這篇的答案需要它** | 討論告一段落時，最多問 **1 題**橋接問題（「這裡為什麼不用 NMS？」這類） | `--how asked` |
   | **跟這次討論無關** | 不要硬問 | 不記錄 |
3. 指令：`python3 mentor.py recall --paper <舊概念的 pid> --result pass|fail --how mentioned|asked|followup --depth <0-4> [--note ".."] [--blindspots "a||b"]`
4. **使用者只想打卡、沒力氣的日子**：完全不做這件事。

**計分（刻意不懲罰）：**
- 通過 → 下次驗收的間隔拉長（3 → 7 → 30 → 90 → 180 天，「該驗收了」的門檻）；技能地圖可升到 4／5。
- 答錯一次 → 只記盲區、間隔歸零，**不扣分、不降技能等級**。同一個概念連續兩次答錯，才算一次 fail。
- 不會有「待考清單」或「還欠幾題」這種東西給使用者看。
- `recall_due` 只在使用者主動說「考我」「幫我複習」時才用。

**done 收尾順序**：`recall`（若有）→ `review` → `journal_add` → `paper_xlsx` → `kb_queue`（若有 paper-kb）→ `light_checkin` → 對話總結。

## 升級規則加嚴（2026-11-11）

## 技能地圖 skill_map（2026-11-11 修復）
- 舊版 `skill_map` 從 7/3 起就沒有任何指令會更新（`review` 不寫入），已修復。

- **自動更新**：`review`／`recall` 會依論文 pid 與標題自動比對技能名稱（例如標題含 DETR → DETR）；也可用 `--skills "DETR||Attention"` 指定，名稱不存在時會新增。
